SQL Formatter

Uppercase keywords, one clause per line, indented subqueries. Dialect-agnostic.

Formatted
—

Worked example

Formatting does not change execution, but it changes review. A query that fits on one line is read as "some SQL"; the same query with clauses on separate lines is read as a set of decisions about joins and filters.

SQL does not care about whitespace, which is exactly why formatted SQL is a communication tool rather than a syntax requirement. The value is in review: a diff of a formatted query shows the clause that changed, not the whole line.

Dialect caveats

This is a keyword-driven formatter, not a parser. It will not understand dialect-specific syntax such as Postgres :: casts or T-SQL TOP, and it will not reorder or validate anything. For anything structural, use your database's own EXPLAIN output.

Formatting rules that survive review

Uppercase keywords and one clause per line make a query skimmable, but the change that matters most in review is placing each join beside the table it joins rather than at the end of a chain. Indenting continuations inside parentheses by two levels also keeps a nested subquery from blending into its host query.

Formatting must never change semantics, so be wary of tools that rewrite: comments can be moved across a formatting pass, and a trailing comma before FROM is legal in some dialects and not others. Keep the original query beside a formatted version when diagnosing, and re-run after formatting rather than assuming the result is unchanged.
