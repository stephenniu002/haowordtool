Worked example

Serving an SVG as text/plain stops it rendering in an <img> tag. Serving it as image/svg+xml renders it — and also allows embedded scripts when opened directly, which is why SVG uploads need sanitising.

The Content-Type header tells the client how to interpret bytes. Browsers sniff when it is missing or wrong, but never for scripts, and modern browsers refuse to execute a script served with the wrong type at all.

Two parameters that matter

charset for text types, and boundary for multipart. Omitting the charset makes non-ASCII content depend on browser defaults, which is how mojibake happens. application/octet-stream means "unknown binary" and forces a download rather than a render.

Why the header beats the extension

The Content-Type header is what the client acts on; the file extension is only a hint for the operating system. A JSON file served as text/html will not be parsed as JSON, and a stylesheet served as text/plain is ignored outright in strict browsers. When a download opens in the browser instead of saving, or a fetch fails to parse, the header is usually the reason.

Add a charset for anything textual — without it, browsers guess, and the guess is sometimes windows-1252. Prefer application/octet-stream only when you genuinely want a download prompt. And do not rely on content sniffing to cover a wrong type: browsers apply it inconsistently and the protections against it are getting stricter, not looser.
