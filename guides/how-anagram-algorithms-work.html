How an Anagram Algorithm Works

A plain-language explanation of letter signatures, multisets, wildcards, filtering, and ranking.

By HaoWord Studio Editorial · 15 min · Updated 2026-10-30

Represent letters as counts

A reliable solver treats letters as a multiset: AELRST becomes {a:1,e:1,l:1,r:1,s:1,t:1}. A candidate is valid when none of its letter counts exceed the rack counts. This prevents a candidate such as TREAT from using two T tiles when only one exists.

Exact and subset searches differ

For an exact anagram, candidate length equals rack length and every count must match. For an unscramble search, candidates may use a subset. The distinction changes both correctness and performance, so the interface should state which mode is active.

Handle wildcards explicitly

A wildcard covers each missing count up to the number of blanks. It should not be converted into a chosen letter before candidate testing. After matching, the interface can highlight which letters consumed blanks so players understand the result.

Rank for human usefulness

Alphabetical output is correct but not always helpful. Ranking by length, then game score, then familiarity puts likely choices first. A transparent rank is preferable to unexplained “AI” ordering; users should know why a word appears above another.

Sorting letters into a signature

The multiset test described above is easy to state but slow if you run it naively against every word in a dictionary of 170,000 entries for every keystroke. Production solvers therefore precompute. The classic trick is the alphabetical signature: sort each dictionary word's letters once, offline, so that LISTEN, SILENT and ENLIST all collapse to the same key, EILNST. Exact-anagram lookup then becomes a single dictionary access — sort the rack, read off the bucket. Signature indexing turns an expensive scan into a near-instant lookup, and it is why exact anagram tools feel immediate even on a phone.

Subset search — finding every word that fits inside a rack, the mode word games actually need — cannot use a single bucket, because a seven-letter rack has dozens of sub-multisets. Solvers handle it in two ways. The first generates every sub-multiset of the rack and checks each against the signature index; with blanks removed, a seven-letter rack has at most 128 sub-multisets, which is cheap. The second walks a trie of the dictionary, consuming letters from the rack as it descends and pruning any branch whose next letter the rack cannot supply. Trie walking visits far fewer nodes than a full scan and naturally produces words grouped by prefix, which is convenient for players hunting a specific opening.

Build the signature index yourself: 6 steps

The index above is not theory — you can build it in a few minutes with any word list. These six steps are the whole implementation:

  1. Load the word list as plain lines. One word per line, no parsing beyond stripping whitespace.
  2. Normalize each line. Lowercase it, and keep only words of 2–15 letters made of a–z. This single step prevents the most common real-world bug: Listen and LISTEN failing to collapse into the same bucket.
  3. Compute the signature. Sort the word's letters alphabetically: LISTEN becomes EILNST, SILENT becomes EILNST.
  4. Group words by signature — and dedupe. Append each word to the list stored under its signature key, skipping words already present. The dedupe matters if you ever merge two lists: without it, the EILNST bucket contains LISTEN twice.
  5. Sort the rack the same way. The rack listen sorts to EILNST — the identical key.
  6. Look the key up. One dictionary access returns the entire anagram family. No scan, no counting loop.
from collections import defaultdict

def signature(word):
    return ''.join(sorted(word))  # LISTEN -> EILNST

index = defaultdict(list)
for line in open('enable1.txt'):            # 1. load the list
    word = line.strip().lower()             # 2. normalize
    if word.isalpha() and 2 <= len(word) <= 15:
        key = signature(word)               # 3. signature
        if word not in index[key]:          # 4. group + dedupe
            index[key].append(word)

rack = 'listen'                             # 5. sort the rack
print(index[signature(rack)])               # 6. one lookup
# -> ['elints', 'enlist', 'inlets', 'listen', 'silent', 'tinsel']

Run against this site's ENABLE list and the EILNST bucket returns exactly those six words: the familiar family (listen, silent, enlist, inlets, tinsel) plus the rarer elints. That last entry is a good reminder of what the index does not do — it finds letter matches, not playable words. Deciding whether ELINTS belongs in your game is a dictionary question, and the index honestly returns it either way.

Wildcards, blanks and fixed letters

A blank tile breaks the counting logic unless the solver treats it as a budget rather than a letter. The standard approach runs the search once per possible substitution only in the worst case; smarter implementations add a deficit rule: a candidate word is playable if the number of letters it needs beyond the rack is no greater than the number of blanks held. During a trie walk, the solver tracks how many blanks have been spent on the current path and abandons branches that overspend. Fixed letters — tiles already on the board that a play must pass through — are handled by splitting the rack: letters before and after the fixed letter are searched as constrained patterns, which is why board-aware solvers ask where the fixed letter sits, not just what it is.

Three search strategies, compared

Every production solver uses one of three approaches, sometimes mixed. The table below compares them on the dimensions that actually decide which one to build:

StrategyExact lookupSubset searchCost per searchBlank handling
Naive multiset scanCount-compare per wordSame scan, looser testScans all ~168,000 entriesDeficit rule per candidate

The practical takeaway: if your tool only needs exact anagrams, the signature index is the whole job and it is nearly free. The moment you add subset search — the mode word games actually use — you choose between generating sub-multisets (simple, fine up to about 10–12 letters) and walking a trie (more code, scales further). Blanks are the expensive part in every design, which is why the deficit rule is worth getting exactly right before optimizing anything else.

Why ranking matters as much as matching

A seven-letter rack with two blanks can match thousands of words. Returning them alphabetically buries the plays a human would actually choose, so solvers rank. Sensible ranking signals include word length (longer plays usually score more and always clear rack space), game score computed from letter values, and the leave — the tiles remaining after the play, where keeping a balanced vowel-consonant mix and avoiding duplicate letters genuinely improves the next rack. Frequency in real text is a weaker but useful signal for learners, who want common words first. This site's solver ranks by usefulness for study and play rather than by raw score alone, and the ordering rule is documented instead of hidden, because a ranking you cannot inspect is a ranking you cannot learn from.

Where solvers disagree

Two correct solvers can return different lists from the same rack, and the difference is almost never the algorithm — it is the dictionary. Tournament Scrabble in North America uses one official word list, international play uses another, and family games often use a general dictionary that admits words both tournament lists reject, such as some proper-derived terms, while excluding obscure valid plays. Definitions differ too: a solver built for vocabulary study may filter out words it cannot define. When a word you expect is missing, check which list the tool loads before blaming the search. What broke when we built one

Merging two lists doubled the buckets. Our first index build combined two public word lists for coverage. It worked — until we noticed the EILNST bucket returned LISTEN twice. Overlapping lists share most of their words, so every shared word appeared once per source. The fix is step 4 of the build above: dedupe on insert. We now treat "merged source" as a synonym for "duplicates until proven otherwise."

The case bug that hid for a week. Early tests used an uppercase rack constant while the list was lowercase. LISTEN sorted to EILNST and listen sorted to eilnst — two different keys, zero matches, and the index looked empty for every query. Lowercasing before the signature computation fixed it in one line, and we have not trusted a case-sensitive pipeline since: normalize first, hash second, always.

The naive scan that felt fine on a laptop and failed on a phone. Our first prototype ran the multiset count-compare against all ~168,000 entries on every keystroke. On a desktop it was merely slow; on a mid-range phone the pause between typing a letter and seeing results was long enough to feel broken. The signature index fixed exact mode completely, and the sub-multiset enumeration (at most 128 lookups for a 7-letter rack) fixed subset mode for normal rack sizes. Measure on the weakest device you support — the laptop lies.

Accented letters need an explicit rule. A tester typed café and the signature became ACFÉ — a key no ASCII word list will ever match. We decided the rule explicitly rather than letting it fail silently: this solver matches lowercase ASCII a–z only, and anything else is rejected with a visible error. Whatever alphabet your solver supports, write the rule down; "whatever the sort does" is not a rule.

Quick review

The strongest habit is to separate hard constraints—letter counts, length, fixed positions—from helpful clues such as frequency and familiar patterns. Use the tool to narrow possibilities, then use meaning and context to choose.

Frequently asked questions

Why do two correct solvers return different lists for the same rack?

The dictionary, not the algorithm. Two correct implementations over the same word list return the same matches; the differences between real tools come from different lists and different ranking rules. When a word you expect is missing, check which list the tool loads before blaming the search.

Is the signature index enough for subset search?

No. The index answers "exact anagram of this rack" in one lookup, but a subset search needs every sub-multiset of the rack — up to 128 lookups for a 7-letter rack — or a trie walk that accepts words at any depth. Exact lookup is the easy half of the problem.

How do blanks change the cost of a search?

They multiply it. In a signature-index design each blank multiplies the sub-multisets you must generate; in a trie walk the solver must track how many blanks each path has spent. The correctness rule stays simple — a candidate passes when its letter deficit is no larger than the blank count — but two blanks are noticeably more work than one.

Why sort the letters instead of hashing the letter counts?

A sorted string is a canonical key that is trivial to compute and trivial to debug: you can read EILNST and see it means "one each of E, I, L, N, S, T." A tuple of 26 counts works equally well as a key and some implementations prefer it. Sorting won here because it is simpler to explain and to inspect.

Do these methods handle 15-letter racks?

Exact lookup stays instant at any rack length — it is always one hash lookup. Subset search is the constraint: 215 is 32,768 sub-multisets, so a naive enumeration gets heavy. Practical solvers cap it with a minimum word length, switch to a trie walk, or both.
